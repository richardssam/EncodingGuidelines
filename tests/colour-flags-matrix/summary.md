# Colour flag behaviour across FFmpeg versions

Each recipe encodes an untagged 16-bit RGB PNG (`sourceimages/chip-chart-1080-16bit-noicc.png`) to 10-bit 4:4:4 Y'CbCr, as you would when making a movie from an image sequence, with the command in the last column. Each cell has these lines, in this order:

| Line | Example | What it is | Correct value |
| :--- | :--- | :--- | :--- |
| Pixels | `bt709/tv (0.244)` | The matrix and range the encoded pixels actually match, out of BT.709/BT.601 and limited (`tv`)/full (`pc`), with the mean error in 10-bit code values. The planes are read without any FFmpeg colour conversion and compared with ideal conversions computed in numpy. | `bt709/tv` |
| Stream tags | `tv/bt709/srgb/bt709` | What `ffprobe` reports as `range/matrix/transfer/primaries`. `?` is unspecified. | `tv/bt709/srgb/bt709` |
| `colr` | `colr 1/13/1` | The MOV/MP4 `colr` atom, as CICP codes `primaries/transfer/matrix` (1 = BT.709, 13 = sRGB, 2 = unspecified). `no colr` means none was written. | `1/13/1` |
| `prores frame` | `prores frame 1/13/1` | ProRes only: the colour description in the ProRes frame header itself, as CICP codes `primaries/transfer/matrix`. ProRes stores it separately from the `colr` atom, and the two can disagree. | `1/13/1` |
| White and max error | `white 943`<br>`max 4/2/2` | The Y' of the 100% white chips (the source's 65535 white), then the worst Y'/Cb/Cr error against the ideal BT.709 limited-range conversion, measured inside the chips (8 pixels clear of any edge). Both in 10-bit code values. This is where the libswscale white level error shows: 943 instead of 940. | `white 940`, max 0 for lossless H.264 (ProRes adds up to about 2 of compression error) |

Values that match the correct result are **bold**.

FFmpeg builds: 6.0 = `6.0`, 7.0 = `7.0`, 7.1 = `7.1`, 8.0.1 = `8.0.1`, 8.1 = `N-124257-g73262c9136`, 9.0 = `n9.0.1-6-g9d4ca21220b`.

* ProRes has no range field, so its range shows as `?` before 8.1, where the decoder started reporting it as `tv`. That is a change in what is reported, not in the file.
* The H.264 encodes use `-qp 0`, which is lossless in x264 at every bit depth (`-crf 0` is only lossless at 8-bit), so their pixel error is the colour conversion alone. The ProRes 4444 XQ encodes add a little compression loss (about 0.2 code values mean, a few code values at worst).
* With a 16-bit source, `scale` (including the one ffmpeg inserts when there is no filter) puts 100% white at 943 instead of 940; `zscale` gets 940. See FFmpegChanges.md.
* `prores_ks` only accepts 10-bit input, but FFmpeg's ProRes decoder always outputs 12-bit for 4444 and 4444 XQ (it picks the depth from the codec tag). ProRes is DCT based and 4444 reconstructs at up to 12 bits, so a 10-bit source comes back as roughly 4x its 10-bit values plus compression error. The pixel comparison scales this back to 10-bit code values.
